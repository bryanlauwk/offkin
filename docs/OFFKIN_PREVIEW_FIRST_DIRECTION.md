# OFFKIN: preview first, then make it real

## Approved journey

Brand / IP → rich concept preview → refine → Request a Quote & Build Proposal → engineering / prototype / production.

Keep the existing editorial layout and exact headline: **Your business DNA. Made collectible.**

The creative positioning is:

- **From IP to “I Want That”**: a tangible, desirable expression of the brand's world
- **Give People Something To Talk About**: discoverable details, narrative and an authored silhouette
- **Make It LIVE**: playful proposed interaction and a path from the concept to a realistic build

Public caveat: **Concept preview. Final design, functionality and pricing confirmed during the build proposal.**

## Creative standard

The supplied travel, cinema and clean-energy reference boards are the richness target for new generated output, not just gallery content. Keep layered silhouettes, expressive scale, rounded collectible forms, story-specific landmarks, small characters and connected micro-scenes. A physical render must look like a desirable authored object, not a flat illustration extruded into a slab or a luxury architectural model padded with foliage.

The supplied illustrated city-book inspiration adds fine hand-drawn black outlines on warm ivory, restrained colour accents that connect roads and ribbons, dense yet navigable isometric collage, playful scale shifts, tiny everyday activity and unexpected oversized object landmarks. Translate this visual logic into each customer's own story. Do not copy the book's composition or characters; do not force Tokyo, yellow roads or a Japanese theme into unrelated brands. Brand-specific colour remains authoritative.

The same object should remain recognizable through world, hero, details, proposed interaction and packaging. Reference conditioning and source-ID checks help preserve lineage, but AI images are not guaranteed identical geometry. Never describe generated multi-angle studies as engineering drawings or a verified assembly.

## Construction belongs in the build proposal

New creative previews do not require a press/reveal template, static choice, finite part/join graph, 16-print-part budget, assembly coverage check or ProductPlan correction. Those were narrowing visual possibilities before the customer had chosen the idea.

The new public path uses bounded creative-design JSON and server-authored `concept-preview-v1` metadata. It retains exact customer identity, story selections, input-size limits, safe website reading, private stored-reference bytes, matching source lineage, provider budgets, cache isolation, cancellation handling and atomic accepted-version updates. Legacy engineering metadata stays readable and validated; it does not constrain new creative previews.

During the later build proposal, assess actual part count, materials, scale, tolerances, mechanisms, electronics, assembly, finishing, cost and production route. CAD, prototypes and testing establish what works before production. Proposed lights or movement in a concept do not establish engineered functionality.

## Honest request handoff

The completed preview keeps its refinement composer and a **Request a Quote & Build Proposal** CTA. There is no selected contact recipient or submission integration. The CTA therefore opens an optional local request draft with quantity, timing, budget direction and priorities, then downloads it. The interface and file clearly say it has not been sent and places no order. Do not invent an email address or imply delivery.

## Showcase boundaries

Keep plain-text brand names with adjacent unofficial/unaffiliated concept labels. New artwork should not embed real logo assets. Tesla studies are about home energy, storage, charging and electric mobility; rockets, Mars and SpaceX are not Tesla business. Concept boards show creative viewing studies and details, not manufacturing or functional proof.

## Release hold

This change is a draft code proposal. Public generation remains paused. Do not infer permission to deploy, merge, enable generation, run paid tests or resume the unused packaging test. Backend and frontend deployment, then bounded live acceptance, require separate authorization. Offline tests cannot establish live image quality or provider compatibility.
