# Activate the linked OFFKIN concept engine

## Goal
Make the main invited-buyer journey generate the approved pair: a collectible hero first, then an illustrated brand-story card derived from the same frozen identity. Keep every existing v8/v9/v10 concept, route, restore path, private asset rule, quota, admin view and proposal request working.

## Implementation
1. **Add a new versioned live contract**
   - Introduce a paired capability and persisted discriminator alongside v10 rather than changing v10 in place.
   - Keep the existing paired manifest, evidence gates, house style, identity hashes and deterministic prompts authoritative.
   - Advertise paired readiness only when its complete server path is enabled; existing readiness flags remain intact.

2. **Research and lock one truthful direction**
   - Reuse the hardened public-website reader, redirect/private-network checks, Firecrawl fallback and current size/excerpt limits.
   - Ask the server planner for exactly one supported story lens and a bounded product plan, then validate it before any image call.
   - Return actionable evidence, lens or plan errors without generating weak images. Owner statements remain clearly labelled when public evidence is insufficient.

3. **Generate and save the linked pair safely**
   - Render the collectible first, save it privately, then condition the story card on validated bytes from that saved collectible.
   - Store each asset independently with the same identity, manifest and specification digest; resume only the missing stage.
   - Preserve the accepted complete pair during revisions and switch versions only after the full dependency closure passes.
   - Reuse existing cancellation, gateway error handling, quotas, cache separation and private signed-image delivery. No public bucket or permission expansion.

4. **Activate the lean buyer journey**
   - Make the primary path: brand → confirmed cited evidence → one of three story lenses → collectible → story card → proposal request.
   - Use honest stage copy without percentages. Keep advanced plan detail and legacy supporting studies behind disclosure.
   - Replace free-form restart refinement with the four approved targets. Require explicit approval when silhouette, symbolism or mechanism creates a new identity; card composition retains identity.
   - Keep `/?engine=paired-draft` as the offline review surface and preserve all legacy/saved links.

5. **Accept paired proposal requests**
   - Extend server validation to accept either a verified two-asset pair or the existing verified four-asset v10 set.
   - Keep requests private, rate-limited and visible only through the password-protected owner inbox. Do not alter old records.

## Verification and controlled release
1. Run paired contract, mocked runner, API/session, proposal-request, security and legacy v8/v9/v10 regression tests; then type and build checks.
2. Inspect the complete journey on desktop and mobile, including stop, resume, restore, targeted refinement and proposal-request validation. Confirm no generation occurs during mocked checks.
3. Deploy the backend, then use GET readiness only to confirm the new paired capability and unchanged legacy capabilities.
4. Run one bounded live acceptance for **A24**: one researched plan, one collectible and one linked story card. This uses workspace credits. Do not retry paid work automatically.
5. Verify citations, saved lineage, restore, identity consistency, OFFKIN house style, exact-text separation and truthful concept-only wording. Do not claim geometry, mechanics or manufacturability are validated.
6. If any gate, provider call or visual acceptance fails, stop with the accepted live experience unchanged and report the blocker and credit usage. If it passes, publish the frontend and verify the public journey and proposal handoff without creating another concept.

## Technical boundaries
- Keep existing models, output limits, feature flags and generation pause value unchanged unless the new paired capability needs its own explicit flag.
- Do not edit generated auth/client/storage/config files or production credentials.
- The new contract gets separate cache/version keys and strict saved-data readers; no destructive migration or reinterpretation of legacy rows.
- The A24 acceptance is an internal quality test and must not be presented as client work or an available product.
